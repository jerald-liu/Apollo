# Phase 4 — UI Design Contract

> Visual and interaction contract for the local Flask grading UI. Tiny single-developer tool. ~10 min usage per iteration round. Generated by gsd-ui-researcher.

---

## Scope Framing

This is **not a product UI**. It is a localhost grading worklist opened in Chrome/Safari on the developer's own laptop, used for ~5–10 minutes per iteration round, by exactly one person (who is also the model trainer and corpus author). No accounts, no responsive design, no marketing surface, no brand. The contract below is intentionally minimal — only what's needed to make the executor's choices deterministic and the auditor's check meaningful.

Everything is locked in 04-CONTEXT.md (D-01..D-17) and 04-RESEARCH.md. This UI-SPEC adds the small layer of visual + interaction decisions those docs left unspecified.

---

## Design System

| Property | Value |
|----------|-------|
| Tool | none (no shadcn, no component library) |
| Preset | not applicable |
| Component library | none — vanilla HTML + minimal CSS |
| Icon library | none — Unicode glyphs only (▶ ⏸ ⟳ 🔎 ✓ ·) |
| Font | system-ui stack: `-apple-system, BlinkMacSystemFont, "Segoe UI", system-ui, sans-serif`. Monospace fallback for run-id reveal: `ui-monospace, SFMono-Regular, Menlo, monospace` |

**Rationale.** Flask serves two Jinja templates (`index.html`, `pair.html`) and one tiny `style.css`. Pulling in Tailwind / shadcn / Radix for a single-user 5-route app is gold-plating that contradicts the "Phase 4 is glue" guidance in RESEARCH §"Don't Hand-Roll". System font keeps the tool feeling honest and functional — matches the developer-as-user audience.

## Layout

**Single page per pair, with a worklist sidebar.** Two routes, two layouts:

### `GET /` — Worklist
- Centered single column, `max-width: 640px`, vertical padding `lg` (24px) top and bottom.
- Title: "Apollo · Grading · run {short_id_or_blank_if_blind}" (under blind mode the run identifier slot is replaced with "blind").
- Progress line directly under title: "{N_graded} / {N_total} pairs scored — {N_remaining} remaining"
- One row per held-out pair, vertically stacked, separated by `sm` (8px). Each row:
  - Left: status glyph (· pending, ✓ done) + pair id (`007`)
  - Right: action — either "Score →" link (pending) or "Re-score" link (done, secondary color)
  - Whole row is clickable; entire row navigates to `/pair/<nnn>`.
- Row order is `random.Random(seed=hash(run_id)).shuffle(pairs)` per RESEARCH §"Blind Grading UX" item 3 — deterministic within a run, varies across runs.

### `GET /pair/<nnn>` — Score one pair
- Same centered single column, `max-width: 640px`.
- Header: "Pair {nnn} · {position}/{total}" (e.g. "Pair 007 · 4/30"). No run-id, no checkpoint, no timestamp visible.
- Audio block (stacked):
  - "Call" label + `<audio controls preload="auto" src="/audio/{nnn}/call.wav">`
  - "Response" label + `<audio controls preload="auto" src="/audio/{nnn}/response.wav">`
  - "▶ Play call → response" button below both players (chains playback; see Interaction Contract).
- Scoring block (stacked):
  - "Call-Response Fit (1–5)" label + 5 radio-style buttons `1 2 3 4 5` rendered as a horizontal segmented control + collapsed anchor strip below ("1 unrelated · 3 plausible · 5 exactly what I'd play").
  - "Musical Coherence (1–5)" — identical pattern.
  - "Note (optional)" `<textarea rows=2>`.
- Footer row: "Submit & next →" primary button (left), "🔎 reveal" link (right, small, secondary color), "← back to worklist" link (left of submit, small).
- Anchors stay visible at all times — collapsed single-line per scale (not on hover, not in a modal). Full anchor text lives in `eval/rubric.md` (which is the source of truth); the in-UI strip is a reminder, not a replacement.

**No sidebar, no nav, no header chrome.** One column, top to bottom, scrollable. The scroll length per pair is ~one viewport on a 13" MBP — no fold concerns.

## Interaction Contract

### Audio playback
- Both `<audio>` elements use native browser controls. The user CAN scrub each independently.
- The "▶ Play call → response" button triggers a JS sequence: pause both, seek both to 0, play call. On call's `ended` event, play response. On response's `ended` event, button label flips back to "▶ Play call → response".
- While the sequence is mid-flight, the button label is "⏸ Stop". Clicking stops both players.
- **No autoplay on page load.** D-07 says response is pre-rendered, but the user controls when audio starts. Autoplay surprises the user and most browsers block it anyway.

### Keyboard shortcuts (single-finger workflow)
The 30-pairs-in-10-min target requires no-mouse scoring once a pair is loaded.

| Key | Action |
|-----|--------|
| `Space` | Toggle play call → response sequence (same as the button) |
| `1`–`5` | Set call-response-fit score to that value (focus moves implicitly; visible highlight on the button) |
| `Shift+1`–`Shift+5` | Set musical-coherence score |
| `n` | Focus the note textarea |
| `Enter` (outside textarea) | Submit if both scores are set; no-op + brief inline hint if not |
| `Esc` (inside textarea) | Blur textarea back to global key handlers |
| `r` | Replay sequence from start |

Shortcuts are documented as a static `<details>` block at the bottom of `pair.html` titled "Keyboard shortcuts" — collapsed by default.

### Submit semantics
- Submit is only enabled once **both** scores are set. Note is always optional.
- On submit: `POST /score` with `{pair_id, fit, coherence, note}`. Server writes both records in one `open(..., "a")` per Pitfall 2 in RESEARCH.
- On 200 response: auto-advance to the next pending pair in the shuffled worklist order. If no pending pairs remain, redirect to `/` (worklist shows all green checks + a "Done" banner).
- On non-200: stay on page, show an inline error (see Error States).

### Score state visualization (the 1–5 buttons)
- All five buttons are visible at all times. The selected one has the accent background + white text; the others have a 1px neutral border and neutral text.
- No tooltips, no transitions beyond `transition: background 80ms ease`. Keep it static and snappy.

### Reveal toggle
- "🔎 reveal" link in the pair-page footer calls `GET /reveal/<nnn>` (returns `{run_id, checkpoint_path, iteration}`).
- Result is injected into a small `<aside>` element at the bottom of the pair page, monospace font, neutral color. Once revealed for a given pair-page render, it stays revealed until navigation.
- No telemetry, no `reveal_used` flag — RESEARCH §"Blind Grading UX" explicitly says the note field stays freeform and reveal usage is honor-system.

### Resumability
- The worklist's "graded" set is computed from `eval/scores.jsonl` filtered to the current `run_id`. Already-graded pairs render with the ✓ glyph and "Re-score" affordance instead of "Score →".
- Visiting `/pair/<nnn>` for an already-graded pair pre-populates the sliders + note with the latest record for that (run_id, pair_id, dim) tuple. Submitting writes new lines (last-write-wins, per RESEARCH Pattern 1).

### Pair-state taxonomy
Three states only. Visible on the worklist; implied on the pair page.

| State | Worklist glyph | Worklist label |
|-------|---------------|----------------|
| Not yet scored | `·` (middle dot, neutral) | "Score →" |
| Scored (both dims present) | `✓` (accent color) | "Re-score" |
| Unrenderable (response.wav missing on disk) | `⚠` (destructive color) | "no response — re-render" (no link) |

The "in-progress" / "partial" state from the prompt is intentionally collapsed into "not yet scored" — a single `POST /score` writes both dims atomically, so partial states only appear on crash and are surfaced as "not yet scored" (i.e. the user just re-scores).

## Spacing Scale

Declared values (all multiples of 4):

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Inline gap between status glyph and pair id; padding inside score buttons |
| sm | 8px | Gap between worklist rows; vertical gap between label and control |
| md | 16px | Default spacing between blocks (audio block, scoring block, footer); page padding on narrow viewports |
| lg | 24px | Vertical padding top/bottom of the column; spacing between the two scoring dimensions |
| xl | 32px | Spacing between major sections (audio block ↔ scoring block) |

Exceptions: score buttons are `40×40px` (multiple of 4, also comfortable mouse + keyboard target). Audio elements use the browser's native sizing — not overridden.

## Typography

Three roles. Two weights.

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 16px | 400 | 1.5 |
| Label / button | 14px | 500 | 1.4 |
| Heading (page title, "Pair NNN · 4/30") | 20px | 600 | 1.3 |

That's it. No display size, no extra weights, no italic. The worklist pair-id and the anchor strip both render as body. The monospace reveal aside renders at 13px / 400 / 1.4 in the monospace stack — that's the only deviation and it earns its keep by visually distinguishing machine identifiers from human text.

## Color

Functional palette. No brand, no gradient, no shadow. CSS custom properties under `:root`.

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#FAFAFA` (background) / `#1A1A1A` (text on background) | Page background and primary text |
| Secondary (30%) | `#F0F0F0` (subtle surfaces) / `#666666` (muted text) | Score-button unselected fill, anchor-strip text, "back to worklist" link, "Re-score" link |
| Accent (10%) | `#0066CC` | Selected score button background, "Score →" link, "Submit & next →" primary button, ✓ done glyph |
| Destructive | `#CC3333` | ⚠ unrenderable glyph, inline error message border-left and text |

Accent reserved for: **(1)** the currently-selected score button on each of the two dimensions, **(2)** the primary "Submit & next →" button, **(3)** the "Score →" action link in worklist rows, **(4)** the ✓ glyph on scored worklist rows. **Not** used for navigation links, not used for the reveal toggle, not used for focus outlines (focus uses `outline: 2px solid #0066CC` in browser default style — that's acceptable accent reuse for accessibility).

The 60/30/10 split is approximate — for a single page of this size, exact pixel measurement is theatrical. The intent (one dominant neutral surface, restrained secondary, minimal accent) is the contract.

| Empty state (response.wav missing for a pair) | "No response audio for pair {nnn}. Re-run the M4L render device against this run's manifest." (Inline on worklist row, no link — the action lives in Ableton, not the web UI.) |

| Error state (audio fails to load) | Browser-native: the `<audio>` element shows its own error UI. No custom overlay. |
| Submit disabled hint | "Set both scores to enable submit." (Inline, neutral text, appears next to the disabled Submit button.) |

**No destructive actions in this UI.** Score records are append-only — "Re-score" just appends another line, it doesn't delete anything. No confirmations needed.

## What This Spec Deliberately Does Not Define

Listed so the executor doesn't waste effort and the auditor doesn't flag absence as failure:

- **Responsive breakpoints.** Single laptop, single browser. Page is `max-width: 640px` centered; the rest is browser default.
- **Dark mode.** Not in scope. The neutral palette renders fine in default macOS appearance.
- **Animation / transitions** beyond the 80ms button background fade.
- **Loading skeletons.** Pages render with data; `<audio>` shows its own native loading affordance.
- **Accessibility beyond keyboard reachability and visible focus.** Single-user single-machine — no screen-reader testing, no contrast certification beyond "the developer can read it." (The neutrals + accent do clear WCAG AA at the declared sizes by inspection, but it's not a contract.)
- **Analytics, telemetry, error reporting.** Flask's stderr is the log. The user IS the bug report channel.
- **Multi-session UI** (e.g. switching between multiple runs in one browser tab). Each grading session is launched with one `--run-id` and that's the run for the lifetime of the Flask process. To grade a different run, kill and re-launch.
