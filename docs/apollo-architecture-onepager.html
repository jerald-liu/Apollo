Apollo · Call-and-Response Generative MIDI Model

Architecture & Decision Rationale

Apollo takes a short MIDI phrase (a call) played through an Ableton Operator FM preset and generates a complementary MIDI response in my own style. The design thesis: build a tool for myself first — where I can be both the domain expert and the only user — then generalize into a paved path for others. Every architectural choice trades generality for a small, learnable, locally-trainable system that sits at the intersection of my music and engineering expertise.

"The model is small on purpose. The hard part isn't scale — it's defining a clean problem where a corpus I can author by hand is enough signal to learn from."

Core Design Decisions — Why & Tradeoffs

Representation

Notes as discrete 4-token groups, quantized to bins

Each note is [time_shift, pitch, velocity, duration] — four IDs drawn from quantized bins on a single 256-wide number line. This reframes generation as classification (pick 1 of N per step), not regression over continuous values.

Win: Classification is far easier to train on a tiny corpus than regressing floats. Quantized bins also match how I actually author — grid-locked in Ableton — so the discretization throws away noise, not signal.
Cost: No micro-timing, no off-grid groove, no continuous dynamics. I'm deliberately living in the "quantized, tiny gesture" regime (2–6 notes, <2s). Humanized timing is a later corpus extension, not a re-architecture.
Forward Compatibility

Vocab reserves 144 empty slots (IDs 112–255)

v1 uses 112 token IDs (notes + BOS/EOS/SEP). The embedding table is allocated at 256 rows; the rest sit unused.

Win: Pitch-bend / mod-wheel / CC tokens can be added later without renumbering any existing ID — so a checkpoint I train today still loads after the vocab grows. Cheap insurance: a few hundred unused embedding rows cost almost nothing.
Cost: A slightly larger embedding table and the discipline of never mutating frozen IDs without bumping a schema version. Trivial price for not orphaning checkpoints.
Conditioning

Mel-condition the call audio via a jointly-trained CNN

The same notes through a bright pluck vs. a soft pad warrant different responses, so timbre is real signal. I render call.wav → log-mel (96×128) → a small CNN → one 128-d "timbre fingerprint," injected as a prefix token the transformer can attend to.

Win: Training the encoder jointly from scratch (vs. a frozen CLAP/AudioMAE) lets it specialize to the narrow, predictable spectral structure of one FM synth family — learnable on a small corpus precisely because the timbre space is bounded.
Cost: A general pretrained encoder would transfer across instruments; mine won't. Accepted — v1 is Operator-only by design. Also a real asymmetry: the mel can capture an LFO pulse in the call, but the response channel is MIDI-only, so the model can answer with note rhythm but not synthesis-level rhythm. Logged as a known limitation.
Model

Decoder-only transformer with a mel prefix token

A causal TransformerEncoderLayer stack (4 layers, 4 heads, d=128) acts as a decoder-only LM. The mel vector is concatenated at position 0; tokens attend back to it. Loss and generation flow left-to-right over [BOS, call, SEP, response, EOS].

Win: One unified attention mechanism handles both "read the call + timbre" and "write the response" — no separate encoder/decoder cross-attention to wire up. Small enough (~976K params) to train and iterate on locally in seconds.
Cost: Prefix-conditioning is less expressive than full encoder-decoder cross-attention. At this scale and corpus size, the simplicity is worth more than the marginal capacity.
Training Objective

Cross-entropy loss masked to response tokens only

The SEP token marks the call/response boundary; loss is computed only on positions at or after it. The model is never graded on reproducing the call.

Win: Forces the model to learn generation (call → response), not autoencoding (copy the input). Every gradient dollar goes toward the actual task. The call is context, not a prediction target.
Cost: Slightly more bookkeeping (find SEP, build the mask with the correct j >= sep_pos boundary — an off-by-one here silently drops the first response token). Worth it; the mask is the whole point of the framing.
Initialization

Train from scratch — no MAESTRO / piano warm-start

A prior milestone trained on MAESTRO piano and hit a representation-level blocker: the 91–95% pedal-active prior was load-bearing in the output distribution. That code is archived on a deprecated branch as reference, not lineage.

Win: Piano priors (pedal behavior, piano dynamics envelope) actively conflict with FM/Operator material. A clean random init learns the right distribution instead of fighting an imported one.
Cost: No transfer-learning head start; I'm fully dependent on corpus quality. Acceptable because the model is tiny and the domain is narrow — from-scratch converges fast.
Generation Control

Learned EOS stop + hard max-token budget

The model learns to emit EOS when a response "feels complete." A max_tokens budget (default 24 = 6 notes × 4 tokens) is a hard backstop. Sampling uses temperature (0.8) + top-k (10).

Win: EOS gives clean variable-length output with near-zero cost (one vocab slot). The budget guarantees termination even if a confused model never emits it. Two layers of safety, both cheap.
Cost: A fixed budget can clip a legitimately long response — but that's out of scope by design (tiny gestures only), so the ceiling doubles as a scope guardrail.

Real-time Max-for-Livev1 is offline .mid → .mid. Validate the musical bar before the latency bar.
Cloud / Modal trainingModel + corpus are small enough for Apple Silicon (MPS). No infra to manage, fast iteration loop.

The Real Product: the Active-Learning Loop

A single trained checkpoint is not the deliverable. The methodology is: author ≥30 pairs → train → listen to held-out responses → score call-response fit (1–5) → identify gaps → author more → retrain → confirm scores moved.

  • 20% held-out, deterministic split (hashed by folder name) — never trained on, so scores are honest.
  • Ship gate: v1 ships only when two consecutive iterations both improve mean held-out fit — proof the loop works, not a single lucky model.
  • Why this framing: it's the part that generalizes. The model is bespoke to me; the loop is the paved path I'd hand to the next person.

The 30-Second Interview Story

"Apollo is a generative call-and-response model for FM synthesis. I built it for myself first — I'm the domain expert and the only user — so I could make aggressive scope cuts most teams can't: monophonic, quantized, tiny gestures, one synth. That let me get to a small model that trains locally in seconds and a corpus I can hand-author."

"The interesting engineering is in the framing, not the scale: discrete tokenization so generation is classification not regression; mel-conditioning so the model responds to timbre, not just notes; response-only loss so it learns to generate rather than autoencode; and a vocab that reserves space for future expression tokens so today's checkpoints survive tomorrow's features."

"The actual product is the active-learning loop — author, train, listen, score, iterate — which is the piece that generalizes from a tool-for-me into a paved path for anyone. That intersection of deep music intuition and ML engineering is exactly where I wanted to build."
